# Content and interface design

The public site implements the [Open Frontier Curriculum](CONSTITUTION.md).
Four foundations lead to integrated praxis. Development, life contexts and learning
practices are distinct routes or supports, rather than competing subject branches.

## Learner model and ownership

- `data/obelisk/` retains source identities, subject records, outcomes, recommendations and evidence attachments.
- `data/learning-design.json` owns foundation and support views, branch display labels and curated journey entries.
- `schemas/learning-design.schema.json` validates those views; runtime checks resolve identities and unique routes.
- `scripts/learning_atlas.py` joins them into generated learner pages and `data/learner-catalog.json`.
- The catalog distinguishes subjects, outcomes and resources; relationship kinds distinguish prerequisites, containment, recommendations and related inquiry.
- Source records marked `record_kind: reading-area` remain separate from identified works/resources in the library and are labelled in subject recommendations.
- Inline source references in attached teaching render as linked titles with original punctuation; unknown source IDs fail generation.
- The generated `docs/project/evidence.md` publishes the current candidate, documentary inventory and explicit limits on validation claims.
- `docs/index.md`, `docs/paths/index.md`, `docs/praxis/index.md` and `docs/project/index.md` are authored entry experiences.
- Generated foundation, subject, library, life and evidence pages are regenerated by `scripts/audit_obelisk.py`; its `--check` gate includes all of them.

One study home per subject combines readiness, available teaching, readings and
onward relationships. The same prerequisite graph drives lists and visual connection
views. Unknown dependencies remain unknown. Philosophy problem families remain
subjects, without claiming that they are atomized measurable outcomes.

Existing IDs are compatibility keys, not learner vocabulary. Three curated routes
have explicit readable slugs. Other routes retain stable ID-based filenames until
an explicit alias migration can preserve all existing links.

Legacy teaching bodies are preserved. Generated compatibility notices and search
exclusions prevent duplicate study homes without removing old URLs. The preservation
audit distinguishes these changes from substantive edits. Source recommendations
attached to outcomes retain their original targets and are labeled accordingly.

## Rendering and verification

Foundation and frontier overviews use expandable rows with purpose, study links and direct resource access.
Filters retain their state in URL parameters. Reading details remain available without becoming a compulsory step before opening a resource.

`data/obelisk/technology-study.json` owns explained editorial technology-to-subject recommendations.
Reverse application links derive from those same records. Unmapped technologies remain explicit; introductory track resources are not technology-specific assignments.

`data/frontier-100.csv` owns frontier titles, classifications, bottlenecks, background study and exercise seeds.
`data/frontier-taxonomy.json` owns class labels and imported provenance.
Track names and routes belong to `data/obelisk/legacy-attachments.json`; durations and entry resources derive from the track CSV sequences.
`scripts/frontier_data.py` reads these inputs. JSON exports, program inventory and browse listings are generated projections.
Technology detail pages retain their URLs; declared source-backed sections regenerate from the CSV, while other authored sections remain separate.

`data/obelisk/preservation-baseline.json` records imported identities that must not disappear silently.
Preservation checks permit catalog additions instead of fixing current branch sizes. This baseline is a migration safeguard, not a completeness claim.

Metadata parsing uses the Markdown `meta` extension. Project and audit pages stay
outside the primary learning routes. Search excludes duplicated legacy reference
and attached teaching pages. Subject and library filters use local JavaScript;
the complete indexes remain visible when JavaScript is unavailable.

Use `uv run --frozen python scripts/build_docs.py` for an isolated clean build in
`.verification/site`. It copies docs into a temporary working directory because
the installed Zensical cache can conflict with a concurrent `zensical serve` process.
`scripts/verify_release.py` uses this isolated build and audits the resulting HTML.

## Reader tasks

Common visits include:

- Find the next subject to study.
- Trace the prerequisites for a technology.
- Pick a primary book for a subject.
- Check the mastery standard for a module.
- Find where history, institutions, economics, or ethics change a technical decision.

Put that information near the top of the page.

## Information design

1. Use descriptive links. Write `Fusion: bottleneck and prerequisites`, not `Learn more`.
2. Lead with four foundations, praxis, study routes and library; keep project administration separate.
3. Use progressive disclosure. Index pages summarize. Module pages contain execution detail. Source pages contain references.
4. Subject pages use readiness, study and practice, reading options and onward connections. Calendar pacing belongs to particular pathways, not subject identity.
5. Design for phones first. Prefer short lists and responsive cards. Use a table only when row-by-row comparison matters.
6. Use standard subject and technology names in headings.
7. Put one factual claim in a sentence when practical. Link primary or official sources for current claims.
8. Label source type: primary research, textbook, empirical synthesis, formal theory, normative argument, memoir, or practitioner method.
9. Remove motivational filler. The subjects, technologies, projects, and sources should carry the interest.
10. Keep sequence and mastery criteria explicit. They are the main editorial judgment of the curriculum.

## Prose

Public prose follows [STYLE.md](STYLE.md). Reference schemas may use fragments. Oral-defense pages may use questions. Technical terminology keeps its accepted meaning even when the word would otherwise be discouraged in general prose.

## AI claims

State the AI hypothesis once on major entry pages. Put current AI claims in the relevant specialization and source pages. Do not use AI as a reason to add repeated future-of-work commentary.

## UI acceptance criteria

The renderer is part of the product. Review the built site, not only the Markdown diff.

- Card titles are inline content. Do not put `h2`, `h3`, or other headings inside card-list items.
- Keep one card schema per index. Title, one short description, then metadata when needed.
- Use one column below 58 rem for modules, specializations, and frontier cards.
- Keep body text at 16 px or larger on common phone browsers. Reference metadata may be smaller but should remain at least 11.5 px at default zoom.
- All keyboard-focusable controls need a visible focus state.
- Color is supplementary. Status badges include the class letter in text.
- Respect reduced-motion preferences.
- Tables may scroll horizontally. Cards and headings must not create horizontal page scroll.
- Test light and dark themes. Dark narrative text, headings, links, and card metadata must meet at least WCAG AA; primary reading colors target 7:1.
- Do not add remote font dependencies. Use the system font stack unless a future design review changes this rule.

Before merging a UI change, inspect these viewports in the browser:

| Viewport | Purpose |
|---|---|
| 390 x 844 | current phone baseline |
| 768 x 1024 | tablet / narrow desktop |
| 1440 x 900 | common desktop |
| 1728 x 1117 | wide desktop |

Check `/`, `/03-specializations/`, one specialization page, `/05-frontier/by-track/`, one feasibility class, and one long module page.

Run the structural checks before browser review:

```bash
uv run --frozen python scripts/audit_ui.py
uv run --frozen python scripts/audit_contrast.py
uv run --frozen zensical build --clean
uv run --frozen python scripts/audit_ui.py --site site
```
